客户端文件预览质量与体验评审

PRODUCT REVIEW · COMPLEX CASE · DESKTOP

PreviewOfficeiTraceQuality Gate
一

问题定义

预览不是打开文件，而是让用户完成下一步
1用户任务

用户希望快速确认内容、继续编辑或发起系统打开；预览页要给出明确的下一步路径。

2当前摩擦

多格式内容的加载、授权、失败提示和重试体验不一致，用户难以判断是文件问题还是系统问题。

评审口径 成功 ≠ 仅仅出现首帧
  1. 加载成功：目标文件在预览容器中稳定展示，且没有错误遮挡内容。
  2. 可继续操作：用户能编辑、切换、系统打开或返回，不被一次失败锁死。
  3. 可诊断：失败能区分权限、路径、格式、网络和渲染终态，并保留可查询证据。

证据边界：单次截图能证明“当时看到什么”，不能单独证明稳定成功率、跨平台能力或线上发布状态。
三

方案比较

优先保证终态清晰和恢复能力
三个方案层级从容器体验到证据闭环
OPTION 01统一状态

把 loading、ready、recoverable error、terminal error 做成统一状态机。

收益：用户知道下一步
→
OPTION 02按 revision 重试

授权 URL、渲染 key 和重试都绑定文件 revision，避免旧内容污染新内容。

收益：降低偶现错配
→
OPTION 03补齐 iTrace

统一记录格式、平台、动作、终态和错误分类，用于后续质量回归。

收益：能复盘而不是猜测
推荐组合：先交付 Option 01，再用 Option 02 和 03 扩大可验证范围。
不纳入首期的内容

跨平台性能排名、真机端到端结论和长期线上成功率，需要冻结版本、统一输入、终态采样和发布关联后再判断；当前仅作为后续验证计划。

四

观测模型

把一次预览拆成可回溯事件链
Preview E2E请求 → 授权 → 容器就绪 → 文件加载 → 用户动作 → 终态
1身份维度

记录产品、任务、文件类型、revision、平台和窗口，保证后续聚合不串样本。

2事件维度

区分诊断事件与终态事件，frame_load_timeout 不直接等于失败。

3动作维度

记录重试、编辑、系统打开、切换文件等动作及其结果，解释“用户为什么离开”。

终态分类 Terminal taxonomy
类别定义看板处理下一步
Success内容可见且主动作可用计入成功观察趋势
Recoverable当前动作失败但重试可恢复单列诊断优化提示与重试
FailureTTL 内无法完成或明确 error计入失败关联版本与根因
Inconclusive证据不足，无法判断终态不强行归类补采样与证据
五

成熟度

从能打开到能持续改进
Level 1 · 可用

主格式能打开，失败由人工排查；适合验证最小产品链路。

Level 2 · 可恢复

有统一 loading、error、retry 和返回路径，用户不会被一次失败锁死。

Level 3 · 可观测

身份、事件、动作和终态齐全，可以按平台、格式和版本聚合。

Level 4 · 可优化

指标与发布关联，能识别回归、定位根因并验证修复收益。

当前判断
功能接近 Level 2，质量证据仍需补齐 Level 3

当前可以推进统一状态和恢复能力建设；跨平台正式比较、长期稳定性和发布结论暂不提前承诺。

验收分解 功能、体验、证据三层
功能层

目标格式可预览、可编辑或可系统打开，失败可重试。

体验层

loading 不误报失败，错误提示能告诉用户如何恢复。

证据层

每个终态能回溯到文件、版本、平台和具体动作。

七

评审结论

可恢复、可解释、可验证
  1. 通过方向：采用统一状态模型，所有格式共用用户可理解的 loading / error / retry 语言。
  2. 保留风险：Office 容器就绪、平台差异和系统打开仍需真实运行面验证。
  3. 下一步：先完成一条 PDF 与一条 Office 代表链路，再基于终态数据扩展。
总结

好的预览体验不是把所有问题隐藏起来，而是让用户知道现在发生了什么、还能做什么、失败后如何回来。
