一

背景与目标

把一次性交付变成可验证的闭环
AI Native 工作台以 Agent 为中枢，把上下文、工程、验证和发布串成一个工作面

3边界

二

总体方案

Runtime · Context · Validation

AGENT AS AN ENGINEERING SYSTEM

Agent 运行时 · 工程上下文 · 验证系统
上下文资产Spec / Rules / Domain Knowledge
Agent 工具Code / Review / Mock
交付容器Workbench / PR / Report
RUNTIMEAI Native规划 · 执行 · 记忆
质量门禁TestCase / Gate / iTrace
知识沉淀Result → Reusable Skill
建设原则
  1. 上下文先行：先让 Agent 能读懂任务、边界和验收标准，再扩大代码生成范围。
  2. 验证前置：每个自动化动作都要有可复现输入、终态判断和失败证据。
  3. 结果沉淀：把成功流程和失败诊断写回规则、知识库或 Skill，减少下一次重复理解。
三

核心流程

需求 → Spec → 代码 → 验证 → 发布
一条可追踪链路每一步都有输入与完成标准
STEP 01澄清需求

明确对象、范围、约束和不做什么，形成可评审的任务卡。

产物：需求摘要 + 风险清单
→
STEP 02生成 Spec

把行为、数据、边界和验收标准写成 Agent 可执行的上下文。

产物：Spec 必须产物 + TestCase
→
STEP 03执行与验证

Agent 实施变更，人审关键判断，自动化检查回填证据。

终态：可提交、可复现、可回滚
核心判断：编码只是链路的一段，真正要提效的是上下文、验证和反馈闭环。
首期能力清单
能力输入完成标准
需求分析需求描述、现状代码、约束范围、风险、验收项明确
代码生成Spec、Rules、TestCase变更可读、影响面可解释
验证闭环测试命令、Mock、日志查询通过或失败均有证据留存
四

风险与验证

先验证边界，再扩大自动化
风险 1｜上下文质量不足

如果 Spec 只写目标不写边界，Agent 会把不确定性转移到代码和测试阶段。首期要求每条需求至少包含对象、约束、验收和明确不做项。

风险 2｜验证终态不清

“页面打开了”不等于“功能完成”。验证必须区分可见结果、系统日志、数据状态和发布状态，不能用截图代替全部证据。

阶段门禁
阶段 A · 试点

覆盖一个前端模块，人工复核全部 Spec 和验证结果。

→
阶段 B · 扩展

沉淀稳定模板，增加固定流程自动 Loop，保留失败回放。

→
阶段 C · 规模化

按真实成功率、缺陷率和复用率决定是否推广。

五

依赖与边界

复杂系统先划清责任面
A平台依赖

需要稳定的任务状态、文件读写、命令执行和日志查询能力；接口失败必须能回传明确错误。

B工程依赖

仓库要提供可读的模块边界、统一规则、测试入口和最小可运行样例，否则自动化无法闭环。

C人的责任

Owner 负责范围、架构、敏感判断和发布决策；Agent 负责执行、记录和反馈，不替代责任归属。

责任矩阵 RACI-like ownership
环节Agent工程师平台最终证据
需求拆解提出候选确认边界提供上下文Spec
代码实施执行变更审查设计提供工具Diff + Check
发布判断汇总信号做最终决策提供门禁Release Record
六

治理与度量

用质量指标约束自动化扩张
治理原则先证明有效，再扩大授权；先保留失败，再讨论提效
过程指标 Process

Spec 完整率、TestCase 覆盖率、验证执行率、人工返工率。

结果指标 Outcome

需求吞吐、缺陷数、Reopen 率、终态成功率和可复现率。

风险指标 Risk

敏感改动数量、失败后重试次数、权限拒绝、跨平台差异。

沉淀指标 Learning

规则复用率、Skill 命中率、失败诊断转化率和上下文更新时间。

推广阈值
没有完整证据，就不做产品排名

试点数据只能说明当前任务和环境下的诊断结果。只有版本、任务、输入、窗口、平台和终态都可比时，才进入正式横向比较。

七

结论与路线图

先做出样板间，再沉淀成团队能力
  1. 本周：选定一个上下文明确的前端模块，补齐 Spec、TestCase 和验证命令。
  2. 下周：跑通一次完整需求链路，保留成功与失败两类证据。
  3. 后续：把稳定流程包装为 Skill，评估是否具备跨团队复用条件。
总结

AI Native 的核心不是“让 AI 多写代码”，而是让工作从需求到验证都变成可理解、可执行、可证明的系统。
